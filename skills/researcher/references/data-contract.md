# Формат исследования

## Команды

Подставляй абсолютные пути как отдельные аргументы с корректным экранированием своей оболочки. `SKILL_DIR` — папка скилла; `STUDY_DIR` — новая папка исследования. Используй доступный Python 3.10+; в Codex его можно найти через инструмент зависимостей рабочего окружения. Не устанавливай Python автоматически.

```text
python SKILL_DIR/scripts/research.py init STUDY_DIR --title "Корпоративный ИИ" --question "Какую платформу выбрать?"
python SKILL_DIR/scripts/research.py check STUDY_DIR
python SKILL_DIR/scripts/research.py check STUDY_DIR --final
```

`init` отклоняет любой существующий целевой путь; режима force нет. `check` только читает файлы и возвращает JSON: код выхода 0 — нет структурных ошибок, 1 — ошибки исследования, 2 — ошибка запуска. `--final` дополнительно требует полного покрытия матрицы, разрешения обязательных критериев и заполненного итогового отчёта. Истинность утверждений он не проверяет; принятое пользователем решение не требуется.

## Десять файлов

| Файл | Назначение |
|---|---|
| brief.md | Вопрос, охват, дата актуальности, ограничения и допущения. |
| task_plan.md | Этапы, состояния и условия завершения. |
| progress.md | Журнал действий, проблем и точный следующий шаг. |
| findings.md | Находки, противоречия и промежуточные выводы с ID доказательств. |
| sources.csv | Реестр источников и их доступности. |
| evidence.csv | Утверждение → источник → поддержка → статус. |
| comparisons.csv | Один текущий результат на пару объект–критерий. |
| report.md | Ответ со ссылками и ограничениями. |
| decision.md | Рекомендация и отдельно решение пользователя с автором и датой. |
| research.json | Машиночитаемые объекты и критерии для контроля покрытия. |

research.json дополняет девять файлов исходного плана для обнаружения пропущенных объектов и критериев. Рабочие материалы принадлежат исследованию, не папке установленного скилла.

## Матрица

```json
{
  "schema_version": 1,
  "title": "Сравнение платформ",
  "question": "Какой вариант удовлетворяет обязательным требованиям?",
  "created_at": "2026-09-08",
  "items": [{"id": "I001", "name": "Вариант A"}],
  "criteria": [
    {"id": "C001", "name": "SSO в выбранной редакции", "required": true, "unit": "да/нет"},
    {"id": "C002", "name": "Стоимость в месяц", "required": false, "unit": "RUB/месяц"}
  ]
}
```

ID непустые и уникальные в своём наборе, без `;`. `required` — обязательность критерия для решения, а не наличие функции. Несоответствие продукта требованию — проверенный отрицательный результат, не пропуск. Весов по умолчанию нет: пользовательские веса и формулу сохраняй в brief/findings.

## CSV

UTF-8 (допустим BOM), запятая, заголовки как ниже. Поля с запятыми и переводами строк записывай штатной CSV-библиотекой в кавычках. Даты — `YYYY-MM-DD`; неизвестные даты оставляй пустыми. Списки ID разделяй `;`.

### sources.csv

```text
source_id,title,url_or_path,publisher,source_type,published_at,accessed_at,access_status,notes
```

- ID, название и адрес обязательны. Адрес — прямая ссылка, постоянная ссылка коннектора или абсолютный путь. Убирай секреты и параметры авторизации.
- `source_type`: `primary`, `vendor`, `secondary`, `internal`, `memory`.
- `published_at`: установленная дата публикации/редакции; `accessed_at`: фактическое чтение или попытка доступа.
- `access_status`: `доступен`, `частично`, `недоступен`. При частичном доступе укажи просмотренные части в notes; при неудаче не записывай невидимый текст.

### evidence.csv

```text
evidence_id,claim,status,source_ids,locator,support,checked_at,valid_as_of,assumptions,based_on,notes
```

- `claim`: одно проверяемое утверждение с контекстом; ID, например, E001.
- `status`: `подтверждено`, `заявление поставщика`, `расчёт`, `предположение`, `не проверено`.
- Для первых двух статусов нужны source_ids, locator и support. Все связанные источники должны существовать, хотя бы один должен быть доступен полностью или частично.
- `locator`: раздел, страница PDF, таблица, дата сообщения или иное местоположение. `support`: краткий пересказ подтверждения или короткая разрешённая цитата; для расчёта — формула и единицы.
- `checked_at`: дата проверки записи; у неподтверждённой — дата оценки её статуса. Пусто допустимо только для `не проверено`. `valid_as_of`: дата, к которой относится факт, если установлена.
- `assumptions`: допущения, обязательны для расчёта и предположения. `based_on`: ID входных доказательств расчёта. Каждая внешняя исходная величина имеет свою запись; циклы запрещены.
- `notes`: ограничения, альтернативные трактовки, противоречащие свидетельства. Разные свидетельства могут иметь отдельные E-ID и связываться в одной клетке.

### comparisons.csv

```text
item_id,criterion_id,value,unit,scope,as_of,evidence_ids,status,notes
```

- Одна строка на пару из research.json. Если единица критерия задана, unit должна совпадать; преобразование единиц оформи расчётом.
- `scope`: условия (редакция, тариф, регион, срок, нагрузка); `as_of`: дата актуальности, если установлена. Условия должны быть сопоставимы по смыслу.
- `status`: `заполнено`, `не проверено`, `противоречие`, `не применимо`.
- Для `заполнено` нужны value, scope и evidence_ids. Ссылка на предположение/непроверенное оставляет клетку неопределённой, даже при наличии значения; это относится и к зависимостям расчётов.
- Для `противоречие` нужны минимум два E-ID и объяснение в notes. Два прочитанных источника могут противоречить друг другу.
- Для `не применимо` нужно содержательное обоснование в notes. Не используй этот статус вместо неизвестных данных или для обхода требования.
- Для `не проверено` в notes запиши причину и следующую проверку. Отсутствие сведений не означает «нет».

При непроверенном обязательном критерии --final возвращает ошибку. Выдай полезный частичный отчёт с ограничениями; не объявляй полный выбор и не меняй required ради зелёной проверки.
